# TTS 小请求场景核查（2026-09-29）

## 结论

TTS 适合纳入“多模态小请求并发推理优化”，但应把研究对象限定为：

> **共享 GPU 上，高并发中文实时语音助手/在线客服的一句话流式回复。**

请求由多个独立会话突发到达；每次只生成一个短轮次，目标音频为 **1--10 秒**，主分析区间建议为 **1--6 秒**。以 Qwen3-TTS 12 Hz codec 为例，小请求可操作地定义为不超过约 **120 个 codec frame**（主区间不超过约 72 个），而不是只按文本字符数定义。文本长度只作为输入特征，因为标点、语速、停顿和语言都会改变实际生成长度。

推荐数据集为 **AISHELL-3**，推荐首先评估 **Qwen3-TTS-12Hz-0.6B** 一类较小的流式 TTS。SGLang Omni 的 Higgs + MPS DP 结果只作为技术基线和机制证据，不能直接当成本机可复现结果，也不能作为本课题的创新点。

## SGLang Omni 的 MPS DP 做了什么

SGLang Omni 的 same-GPU data parallelism 不是在一个进程内增加 batch，也不是用 libsmctrl 把 TPC 固定切开，而是：

1. 在同一张 GPU 上启动多个完整 TTS serving replica；
2. 每个 replica 有独立进程、调度器和 KV pool，默认还各自持有一份模型权重；
3. 通过 CUDA MPS 让不同进程的 kernel 在硬件允许时真正并发，而不是让多个 CUDA context 主要依靠时间片切换；
4. 由外部 router 把请求分发到多个 endpoint；MPS 本身不负责请求路由；
5. 为每个 replica 固定相同的 KV 容量，并分配互不重叠的 CPU core，启动后核查进程是否真实出现在 MPS client list 中。

它简单但有效的原因是 TTS serving 同时存在两类空洞：

- **空间空洞**：流式首包延迟限制了单 replica 可以使用的 batch，0.6--4B talker 在小 batch 下可能只有低占用 kernel；
- **时间空洞**：sampler、参考音频预处理、vocoder 调度、chunk assembly 和 HTTP streaming 都有主机侧工作，一个进程的 GPU kernel 发射之间会出现间隙。

多个独立进程可以用一个 replica 的 kernel 填另一个 replica 的主机调度间隙，同时用 MPS 合并来自不同进程的可并发 kernel。它与本课题已有“小图像请求吃不满 GPU，天然适合并发”的观察具有相同结构：优化对象都是**延迟约束下无法靠单请求或深 batch 填满 GPU 的短请求**。

关键差异是 TTS 是自回归或分阶段的流式生成，不是一次固定形状的视觉编码前向。请求成本由输出音频时长、codec frame 数、参考音频预处理和 vocoder 工作共同决定；最重要的延迟指标还包括 time-to-first-audio（TTFA），不能只测完整请求完成时间。

## 官方结果及其边界

SGLang Omni 在一张 H100 80 GB 上使用 `bosonai/higgs-tts-3-4b` 和 Seed-TTS English：

| 配置 | 名义吞吐 | 相对单副本 | 完成情况 |
|---|---:|---:|---|
| Single c96 | 21.7--22.1 qps | 1.0x | 4/4 |
| DP2 + MPS，2 × c64 | 31.5--37.7 qps | 1.4--1.7x | 5 次尝试中 3 次名义完成 |
| DP3 + MPS，3 × c64 | 39.9--46.9 qps | 1.8--2.1x | 4 次尝试中 2 次名义完成、1 次退化 |

单 Higgs replica 在已经到达吞吐平台时约为 29% SM Active；DP2 在不启用 MPS 时约为单副本的 1.24x，说明多进程本身已能回收一部分空洞，而 MPS 进一步允许跨进程 kernel 并发。失败记录包括 `cudaErrorMpsRpcFailure`、replica 启动失败和一次仅 13.3 qps 的退化运行。因此只能得出“该固定 H100 + Higgs 配置下有明显收益”，不能声称 TTS 或所有 GPU 上均能按副本数线性扩展。

MPS DP 的必要条件是：调优后的单 replica 在延迟 SLO 下仍明显低占用、模型及多个 KV pool 能同时放入显存、每个 replica 有足够独占 CPU core、且 offered load 足以分别压满所有 replica。SGLang 文档给出的经验筛选线是单 replica 约不高于 60% SM Active；这只是筛选规则，仍需 A/B 实测。

## 场景比较

| 场景 | 小请求与并发是否自然 | 主要 SLO | 主要问题 | 判定 |
|---|---|---|---|---|
| 多用户实时语音助手 / 在线客服的一句话回复 | 多会话同时产生 1--10 秒动态回复，不能长期攒批 | TTFA、音频不中断、P99 完成时间 | 突发、长度异构、短回复低占用 | **主场景** |
| IVR / 导航固定提示音 | 句子短、并发真实 | 首包与完成时间 | 大量话术可预生成和缓存，在线 TTS 优化价值容易被缓存消解 | 只作为动态变量话术补充场景 |
| 游戏 NPC 动态对白 | 多 NPC 和玩家可产生并发短句 | TTFA、表现力、角色一致性 | 风格与多角色质量变量多，缺少统一系统负载和质量基准 | 有应用价值，但不宜作为首个实验 |
| 无障碍朗读 / 有声书 | 通常是长段连续生成 | 首包、播放连续性 | 主要瓶颈是长序列生成，不属于本研究定义的小请求 | 排除；仅短通知朗读可作为补充 |

主场景可具体化为：一个中文语音助手或客服平台在同一张 GPU 上服务多个会话，每个上游 LLM 完成一句回复后立即调用流式 TTS；文本按开放环泊松到达叠加突发，输出在 1--10 秒内，客户端收到首个可播放 PCM chunk 即开始播放。不同请求可以选固定客服音色，避免把 voice cloning 的额外预处理混入第一阶段的并发机制判断。

## 数据集：AISHELL-3

AISHELL-3 是当前主场景更合适的训练与负载来源：

- 普通话多说话人 TTS corpus；
- **85 小时、218 名说话人、88,035 条录音**；
- 下载包约 **19 GB**，由 OpenSLR 公开提供；
- 提供汉字与拼音转写，官方说明转写标注准确率高于 **98%**；
- 许可证为 **Apache-2.0**；
- 按总时长和句数计算，平均每条约 **3.48 秒**，天然落在本研究的短回复主区间，而不是把长篇音频人为截断后冒充小请求。

使用方式：训练工作沿用官方划分；系统评测从 test 部分构造带 speaker、文本、真实时长的开放环 trace，并按真实时长分为 `1--3 s`、`3--6 s`、`6--10 s`。AISHELL-3 是录音棚式朗读而非真实客服对话，所以它能够提供干净、可复现的中文短句和多说话人质量基准，但不能单独证明真实对话流量分布。后续应另行采集或合成匿名的到达时间、文本长度和会话突发 trace，只替换负载分布，不改变音频质量测试集。

英文复现实验可使用 SGLang 已适配的 Seed-TTS English objective set；其官方仓库说明英文部分来自 Common Voice，并提供 WER 和 speaker similarity 计算脚本。但仓库未给出明确 LICENSE 文件，因此不把它选作唯一主数据集。

## 模型选择与本机可行性

首选候选为 `Qwen/Qwen3-TTS-12Hz-0.6B` 系列：SGLang Omni 已提供 `preprocessing -> tts_engine -> vocoder` serving、24 kHz 增量流式输出和 `0.6B` 配置，官方实现使用 Apache-2.0。固定客服音色时优先用 CustomVoice；若使用 Base 做 voice cloning，必须把参考音频预处理成本作为独立阶段记录。

不能直接采用 SGLang 的 Higgs MPS 配置作为本机方案：

1. 官方 case study 是 **H100 80 GB**，而当前设备是 **RTX 4060 Laptop 8 GB**；
2. 文档记录 Higgs 3--4B 的 AR backbone 单份权重约 7.55--7.60 GiB，尚未计入 codec、vocoder、KV、CUDA Graph 和运行时内存，因此本机无法复制 DP2/DP3；
3. 官方 Higgs 配置给每个 replica `max_total_tokens=100000`，同样是面向 80 GB 卡的设置；
4. CUDA MPS 官方支持对象是 64-bit Linux；当前 WSL2 环境不能被视为已验证的 MPS 实验平台。正式复现应使用原生 Linux，并在启动后检查 MPS client attachment；
5. 即使换成 0.6B 模型，也不能预设 8 GB 一定能放入两个完整 replica。必须先测单 replica 峰值显存和吞吐平台，再做 DP2 启动预检；放不下即停止 MPS DP 路线，而不是用 proxy 结果代替。

因此，TTS 方向在研究问题上可行，但**当前机器能否进行同卡多副本实验仍待先决验证**。较稳妥的执行顺序是：先在现有 GPU 上建立单 replica 的长度--TTFA--吞吐--SM Active 曲线；再在原生 Linux / 更大显存 GPU 上验证 DP2；最后才比较更多 replica 或权重共享。

## 实验设计

至少包含以下基线：

1. 单 replica，关闭额外等待，扫描 client concurrency 到吞吐平台；
2. 单 replica + runtime 自带 continuous/dynamic batching；
3. 两个独立 replica，不启用 MPS，用于分离多进程调度效应；
4. DP2 + MPS，固定相同 KV 容量、CPU core 和总 GPU；
5. 若设备支持，再比较单进程多 stream 或其他共享 GPU 并发方式。

负载不能只用闭环 concurrency。应同时使用开放环泊松到达、短时突发和持续过载，按输出时长混合，并确保每个 replica 都被压满。所有配置至少重复 5 次，报告失败和退化运行，不能只保留最佳吞吐。

系统指标至少包括：

- 请求吞吐率与生成音频秒数/墙钟秒（`audio_s/s`）；
- 平均、P95、P99 端到端完成时间；
- 平均、P95、P99 TTFA；
- real-time factor（RTF）；
- SM Active / GPU 利用率、显存和 CPU 利用率；
- TTFA SLO 与完成时间 SLO 违约率；
- 排队拒绝率、失败率、MPS RPC/启动失败；
- 质量护栏：ASR WER/CER、speaker similarity、UTMOS 或主观 MOS。

建议第一阶段 SLO 暂定为 TTFA `<= 200 ms`、1--6 秒请求端到端不超过对应音频时长（RTF `<= 1`），再按单 replica 实测分布校准。不能用 SGLang 在 H100 上报告的 55--58 ms TTFA 直接作为本机目标。

## 创新边界与停止条件

**同卡多副本 + CUDA MPS 本身已经由 SGLang Omni 实现并公开验证，不能作为本课题创新。** 可研究的内容只能建立在这一基线上，例如：

- 根据预测音频长度、当前 TTFA slack 和 replica 队列状态做请求路由；
- 在单 replica 深 batch与多 replica MPS 并发之间动态切换；
- 面向短请求突发的 admission control 与尾延迟保护；
- 在相同总 GPU/CPU/显存预算下比较 MPS 共享、批处理和单进程并发。

停止条件：若调优后的单 replica 已接近 GPU 饱和；DP2 无法在目标设备显存内启动；或 MPS 在相同资源和质量约束下不能稳定改善吞吐--TTFA/P99 Pareto 前沿，则不继续增加调度复杂度。长篇朗读、有声书和几十秒以上连续生成不纳入“小请求”主结论。
