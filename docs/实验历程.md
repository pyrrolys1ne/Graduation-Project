## 一、在做什么

**一句话**：同一个视觉编码器（CLIP ViT-B/32）、同一块 GPU 上多个请求怎么调度。
目前找到的唯一有效杠杆**不是"同时跑几个"，是"合并几个"**。

### 1.1 研究问题

**M1（落点）** 面向 encoder 单模型单 GPU 多请求并发，什么调度方法能在吞吐率、平均延迟、
P99、GPU 利用率、SLO 违约率上稳定优于**串行执行**与**固定资源分配**？

**M2（特色支撑）** 让调度器知道**自己什么时候可以相信离线标定表、什么时候必须回退**，
是否带来可测量增益？

> ⚠️ **M1 的形态已修正**：原写作"SM 分配与并发调度方法"。实测已否定"切多少 SM"这条轴——
> 真实 TPC 互斥分区被不分区并发严格支配（计算受限时仅为后者的 **53%**）。
> 控制点因此改为**执行粒度**：何时并发 / 何时合并成批 / 何时串行。

### 1.2 研究区间（严格限定，超出不外推）

| 维度 | 范围 |
|---|---|
| 研究对象 | **单个视觉编码器节点内部**的请求级并发；不涉及 prefill / decode / 完整 MLLM 服务 |
| 模型 | CLIP ViT-B/32（patch 32×32），不修改模型结构 |
| 硬件 | 单张 RTX 4060 Laptop（24 SM = **12 TPC**，CC 8.9），8 GB |
| 平台 | WSL2，驱动 610.62（CUDA UMD 13.3），PyTorch 2.11.0+cu128 |
| 资源控制 | **主轴**：多流共驻数 + 按尺寸成批；**辅助/对照**：`libsmctrl` 回调路径 + 粘性线程掩码，TPC 粒度 |
| 请求规模 | 224 / 288 / 336 / 384 / 448 / 512 / 672，单请求单图 |
| 不做 | 多卡、集群、MPS/Green Context/MIG、抢占、模型结构修改、精度优化 |

### 1.3 平台与实验的两段安排

1. **先期平台无法锁定 GPU 时钟**：`nvidia-smi -lgc` 需要 root，WSL2 下通常也不支持。
   文献中同代同 SM 数的 OSPERT'25 锁了频、得到干净结果，本课题没锁、**反而暴露了不可复现性**。
   → **正式实验在实验室服务器上补做锁频 vs 不锁频的对照**，把这条从"条件差异"变成"对照项"。
2. **先期平台拿不到 TPC→GPC 映射**：`libsmctrl_get_gpc_info()` 依赖 `nvdebug` 内核模块，
   本机未加载、无 root。已实测掩码身份对本机性能无显著影响（六种子集极差 **1.008×**），
   故不影响主要结论，但分区只能以 TPC 掩码集合描述、不能归因到具体 GPC。
   → 服务器上补做。

**注意（2026-09-28 用户口径）**：**不把平台条件写成研究边界或缺陷**。本机是初步验证平台，
服务器是正式测试平台；上述两项是**两段安排**，不是硬约束。

## 二、主线：四次转向，每次都是被上一次的测量逼出来的

| # | 阶段 | 做了什么 | 结果 |
|---|---|---|---|
| ① | **DACC** | 写一个把互补性、deadline、优先级、队列风险统一打分的调度器 | **被朴素基线支配**。诊断：损害不在评分逻辑，在架构（窗口 churn，K 越大越差） |
| ② | **标定表** | 转向问"调度器依赖的那张表本身可信吗" | **发现本课题最硬的机制**：小请求的配额→延迟曲线里 **59% 不是 GPU 时间，是主机侧 kernel 发射**，随尺寸单调降到 672 的 7% |
| ③ | **并发度控制轴** | 审计发现本课题全部历史实验里并发度都是启动时常量，而文献里的并发机制全是控制回路 → 把它实现出来 | **被 `static_2` 稳定支配**。归因三条：方向错、信号不是负载的函数、机制在 host 发射 |
| ④ | **换掉发射路径**（当前） | 用 CUDA Graph 把 host 发射压到约 1/1000，并把 CPU 造图与回放拆成两级线程池 | **塌陷消失**。再问"还剩哪些自由度"→ 共驻度失效、配对纯加性、**只有成批还有杠杆** |

**这不是四个方向，是一根链条**：①的负结果逼出②，②的机制逼出③的归因，③的归因逼出④。
而④恰好落在任务书自己预留的位置上——"方法的资源控制点可能不在'切多少 SM'上，
而在**何时并发、何时合并、何时串行**上"。

### 2.1 为什么"分区"这条主流路线被排除

这是理解全局的关键。真实 TPC 互斥分区**在所有负载、所有指标上都劣于共享 SM 的多流**：
计算受限时分区并发仅为不分区的 **53%**；服务级过载下吞吐 −6.0%、P99 +6.7%、SLO 违约 4.1 倍。

**原因**：互斥 TPC 下的计算侧干扰本来 ≈1.0×，**分区能防的干扰本就不存在**；
而 SM 被划死后，硬件**无法把一个请求的 block 填到另一个请求的 SM 上**——
共享 SM 时那种"用等待显存的时间跑另一请求"的填空机会被消灭。**分区分不到好处，却付了实打实的代价。**

### 3.1 已确证（A 级：多轮重复 + 受控对照 + 哨兵合格，可直接写论文）

1. **标定表的可复现性有强烈尺寸依赖**：672 跨轮极差 1.001–1.035×、224 高达 1.936×，
   中间是渐变噪声带、**没有可指认的阈值线**（§10）。
2. **机制是 host 侧 kernel 发射开销**：224 占比 59% → 672 为 7%，单调；graph 回放把四个尺寸
   全部压到 **0% 慢模态**。**已由另一批脚本、另一会话独立复现**（§10.5、§23.1）。
3. **真实 TPC 互斥分区被不分区并发严格支配**（§7 补充、§10.2）。
4. **以队列尺寸混合驱动的动态并发控制器被 `static_2` 稳定支配**：开环、5 轮、
   35 轮哨兵全合格、逐轮配对差全部同向（**§21.3**）。
5. **共驻与配对成本对尺寸纯加性——⚠️ 但仅限图回放路径**：两次独立复现（比值 0.959–1.095、
   中位 **1.009**），且两条 lane 的 span 与单流**逐位相同**（§24.1）。
   **eager 路径下同一件事是 2.0–3.5×（§35.4）**，因为 host/Python 层回到了关键路径上。
   → **"共驻免费"是路径属性，不是 GPU 属性**；引用的必须注明是哪条路径。
6. **两个延迟口径陷阱**：`server_*` 与 `client_*` 相差 15–34 倍、混用会整体翻转结论；
   客户端连接上限会伪装成"饱和实验结论"（§21.1–21.2）。
7. **负结果**：DACC 被支配；分区身份不成立（极差 1.008×）；
   **§5 的"分区并发优于串行"表已于 2026-09-29 撤回**（无产物，见第五节 5.2）；
   任务书 E1 的"分区并发"两个数字重跑后未复现。

**第 5 条同时给第 4 条提供了理论解释**：共驻成本对尺寸可加，所以"尺寸混合"测的是总工作量——
而"总工作量决定吞吐"本来就不需要控制器。**旧控制律不是调参没调好，是信号本身与决策无关。**

### 5.1 最要紧的三条

1. **配额层（"按边际违约收益分配 SM"）相对同 harness 的共享并发，零测量。**

2. **"共享并发违约而动态配额避免"的具体组合给不出，且能说明为什么给不出**——
   图回放路径上共驻可加（没有可防的伤害），eager 路径上的伤害来自 host/GIL（掩码治不了）。
3. **支撑"分区被支配"的量化证据，其输入本身不可复现**：仓库里并存**五份互不相同**的配额曲线；
   小请求上档位差**小于单格标准差**。

### 5.3 数据格式：装不下要用的模型

- `scripts/profile_encoder.py:57-60` 只写 `median/mean/std/samples` 四列，**原始样本被丢弃**，
  `--repeats` 默认 5、每单元实际 **7 个样本**。→ **任何尾部/违约概率都估不出来。**
- 数据**没有 `session_id`、没有执行机制标签**——跨会话与跨路径（eager/图回放）的样本混在一起，
  而 §35.4 已实测同一 `(尺寸, 配额)` 单元在两条路径下的共驻代价相差 2–3 倍。
- 峰值标定直到 2026-09-29 才有（本卡 fp16 GEMM 持续峰值 **~31 TFLOP/s**）。
  **在此之前所有"利用率/百分比"论述都没有正确的分母。**

### 5.4 方法层：只有设计，没有验证

| 缺什么 | 说明 |
|---|---|
| **配额层没有挂载点** | 见 5.4.1——这是比"未验证"更前置的问题 |
| **概率模型** | `P(违约 | 尺寸, 配额, slack)` 与边际收益 Δ **完全没有实现**，也没有数据格式支撑 |
| **排队项建模** | `W` 从未被单独建模或验证——而历史证据显示**损失全在排队**（§4.3、§21–22） |
| **会话切分验证** | 从未做过。现在的做法是**同会话重跑**，只能测会话内离散度、测不到跨会话 |
| **排序检验** | 从未做过。EVP 只需要 Δ 的**排序**正确，这个检验比概率校准弱得多且是真正需要的 |
| **尺寸相关偏置的处置** | §31 已测出表偏置是**尺寸相关**的（224/336/672 高 23–48%、448 低 4%），**未处置** |
| **`default.csv` 重标定** | 一次**判据校准**（会把哨兵对 224/336/672 的严格度从 ~1.9× 收紧到 ~1.5×），须作为决策、不能顺手改 |

#### 5.4.1 ⚠️ 配额层与图回放主路径无法并存（2026-09-29 已判死）

不是"还没有挂载点"，是**在当前平台上没有可行的挂载点**。三条可能路径全部实测封死：

| 路径 | 做法 | 实测结果 |
|---|---|---|
| 1. 回放时设掩码 | 回调路径的线程掩码 | **无效**（0.84×，§11.5；本轮复测 C/A = 1.002） |
| 2. per-stream 掩码 | 硬编码路径写在 stream 结构里 | 本机驱动（CUDA UMD 13.3）调用即 `exit(1)`；**硬编码路径本身不可用** |
| 3. 掩码烧进图（捕获时施加） | 让掩码成为图的一部分 | **无效**（B/A = 1.003，本轮实测） |

标尺：同一会话内 eager 在 3 TPC 下确实慢 1.87×——**掩码机制本身是好的，是图回放绕开了它**。
产物：`results/reproducibility/probes/diag_mask_in_graph_capture.json`。

**后果**：任务书里"请求级 SM 配额"与"图回放主路径"这一组合，按事先写定的死亡判据
**作废**；M2 只能改为在非图回放路径上评估，或整体删除。这也回答了此前挂在
AGENTS.md §8 的「CUDA Graph 方向」判定问题。

### 5.5 未解释的技术缺陷（都不阻塞主线，但都不可解释）

| 缺陷 | 状态 |
|---|---|
| **fp16 下 `encode_batch` 返回 NaN 嵌入** | 边界收窄到"读到未写入/已被复用的显存"，**根因未定位**，需 compute-sanitizer |
| **多 lane 图回放挂死** | 触发条件已定位（多张图同时在 GPU 上执行），**根因未定位到驱动层**；只能 `slots=1` 规避，代价 **−29% 吞吐** |
| `apply_quota` 配额池不足时**静默返回错误字典** | 本轮踩到两次。不抛错、不告警，只少一个 key |

### 5.6 平台与工具

- **锁不了频**（`nvidia-smi -lgc` 需 root）→ 与 OSPERT'25 等锁频工作存在条件差异。
- **拿不到 TPC→GPC 映射**（需 `nvdebug`）→ 分区只能以掩码集合描述，不能归因到 GPC。
- **`ncu` 不可用** → 占用率/气泡只有 NVML 松上界，无法区分"算力忙"与"带宽忙"。
- **A100 上"请求级动态 SM 分配"做不到**：libsmctrl 被禁、Green Contexts 需 CC 9.0、
  MPS 百分比**运行中不可改**、MIG 只有 1/7 粒度。可实现的最强形式是
  **"分区静态、选择动态"**（预建若干 MPS 档位，调度器动态派发）——与先期平台语义不同，必须分别报告。

### 5.7 实验规模

- **400 请求的单批无法验证 10% 的违约率声明**：10% 只有 ~40 个事件，率的 95% CI 约 **±9pp**。
  要区分 10% vs 40% 需要 **≈1000 请求**。
- 每单元要估计 10% 分位，需要 **n ≈ 30 个会话内样本**（序统计量界），现在只有 7。
- **跨会话稳定性从未验证**：本轮两次复现都是**同一会话内**的。

### 5.8 一个未被消解的框架张力

**更新（2026-09-29）**：任务书已按"不轻易外推"重写，处置方式是——把 M1（执行粒度）定为
方法主体且只保留已验证部分，把 M2（SM 配额分配）与 M3（标定表可用性）明确标为
**待检验的附加轴**，并各带事先写定的死亡判据；1.3 节列出八条"尚未确立的"。
即：**张力被如实标注，而不是被论证掉了**。叠加 5.4.1 的实测（三条挂载路径全封死），
M2 在**当前平台**上已无落地形态。

开题时仍须正面回答的问题因此收窄为一个：**在一张本地消费级 GPU、24 SM、禁用
libsmctrl 与 Green Contexts 的条件下，"动态 SM 分配"究竟以什么形态出现在论文里——
是作为被否证的对象，还是作为服务器上待检验的轴。**

课题简介要求"**动态调整 SM 分配**"并以 **libsmctrl** 为底层工具；而实证把这条轴否掉了，
有效杠杆是**执行粒度（何时并发/合并/串行）**。任务书现在的处置是**重构叙事**，不是改简介。
**张力被安置了，但没有被消解**——开题时须正面回答。
