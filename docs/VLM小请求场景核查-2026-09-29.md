# VLM 小请求场景核查（2026-09-29）

## 结论

**建议把主场景定为：RSICD 的 224×224 遥感 tile 图文检索；再用 OpenVLA-224 和 FashionIQ-CLIP 224/336 分别补充强实时场景与高 QPS 业务场景。**

RSICD 的优势是尺寸证据最硬：10,921 张图全部原生固定 224×224，每图 5 条描述，完整语义单元就是一个 tile，不需要借 resize 或动态切片制造“小请求”。这使它最适合先验证“小请求吃不满 GPU，因此可从并发/组批获益”的机制。FashionIQ 更像真实在线业务，但只能确认模型输入可设为 224/336，不能声称原图统一为小尺寸；OpenVLA 则给出明确 224px 骨干与 REST serving，可验证严格延迟 SLO。

主线实验应先使用 **CLIP ViT-B/32、RSICD 原生 224×224 tile + 短文本**，再增加 336/448/672 的受控 resize 档做机制边界对照。后几档是 processor 输入，不应伪称为数据集原始分辨率。

## 尺寸口径

必须同时记录三件不同的东西：

1. **raw resolution**：数据文件原始宽高，只影响解码、上传和缩放成本，不能直接代表 GPU 上的视觉工作量。
2. **processor input**：真正送入视觉编码器的张量尺寸。OpenAI CLIP 官方实现按模型的 `input_resolution` 执行 `Resize` 和 `CenterCrop`；ViT-B/32 的标准输入是 224×224。[CLIP 官方预处理代码](https://github.com/openai/CLIP/blob/main/clip/clip.py)
3. **视觉 token / patch 数**：由 processor input 与 patch size 决定。ViT-B/32 在 224 下是 7×7=49 个 patch；本项目 336/448/672 对应约 100/196/441 个有效 patch。LLaVA-1.5-336 使用 ViT-L/14 时则是 24×24=576 个 patch token；它虽然也是 336 小图，但单请求视觉序列并不等价于 CLIP-B/32 的 336 档。

因此，本课题所说“小请求”应以 **encoder 实际输入和视觉 token 数较少、单请求不能充分占满 GPU** 定义，而不是只看 JPEG 文件尺寸。

## 四类重点候选对照

| 候选 | 请求形态与尺寸证据 | 并发与评价 | 与现系统贴合度 | 判定与风险 |
|---|---|---|---|---|

## 推荐顺序

### 1. RSICD：主场景与机制基准

建议把系统表述定为“**面向遥感 tile 图文理解的多模态小请求并发编码服务**”。最小可复现实验使用 CLIP ViT-B/32、RSICD 原生 224×224 图像和短描述，构造持续 tile 流与突发到达；比较 serial、共享多流、dynamic batch 和请求尺寸/截止期感知策略。质量用双向 Recall@K/mR，系统评价至少报告吞吐率、mean/P99、GPU 利用率和 SLO 违约率。主要限定是：结论只覆盖 tile 级请求，不覆盖一次提交整幅大图再切成大量 tile 的父请求。

### 2. OpenVLA-224：强实时应用验证

OpenVLA 官方模型采用 `prism-dinosiglip-224px`（早期版为 `siglip-224px`），请求是单张相机图像加一条动作指令，官方仓库还提供 REST serving，因此“多机器人/多摄像头共享一个推理节点”是自然的并发场景。[OpenVLA 官方仓库](https://github.com/openvla/openvla) 它比 VQAv2 更有延迟 SLO 意义，但完整 7B action model 会引入语言侧成本，必须把 encoder latency 与端到端 action latency 分开报告。

### 3. FashionIQ：高 QPS 业务验证

请求包含 `reference_image + modification_text + deadline`；商品库 embedding 离线生成，在线路径是小图编码、短文本编码与检索。最小可复现实验使用 CLIP ViT-B/32 的 224 输入、三类商品混合，并用官方 Recall@10/50 验证语义结果。它的业务叙事最强，但 raw 尺寸证据弱于 RSICD，必须表述为“模型输入小”，不能表述为“数据原生固定 256×256”。

### 4. VQAv2/LLaVA-1.5-336：MLLM 对照

它能直接对接“VLM 服务”叙事，336 输入也有官方模型实现。缺点是 7B LLM 的 prefill/decode 很容易成为主要成本。建议只在主线机制确定后，用 encoder-disaggregated 或固定短答案设置验证，不要一开始就把完整 LLaVA 作为调度对象。

Hateful Memes 可作为第五个“短文本二分类”应用，但在完成数据访问、raw 尺寸分布审计和 224 下准确率损失检查前，不应放到前三。

## 其它类别的核查与排除

- **通用图像分类/普通 CLIP 检索**：ImageNet、Food-101、CIFAR 等可做 224 小图，但单个请求只有图像，没有运行时文本条件，严格说不是多模态请求。可作视觉 encoder 压测，不适合作为 VLM 主场景。
- **文档/票据/OCR、DocVQA、ChartQA**：通常需要保留小字号文字、长宽比或使用高分辨率切片/动态 patch；把页面压到 224–672 往往改变任务本身。它们会把 OCR、tiling 和长视觉 token 引入系统，**排除出“小请求”主线**。
- **医学影像**：胸片图文检索/报告匹配可用 CLIP/MedCLIP 的 224 processor，形式上合适；但原始胸片常为高分辨率，缩到 224 可能丢失微小病灶，且数据许可、隐私和临床正确性使复现门槛较高。可作为后续领域验证，不作首选。[MedCLIP 官方仓库](https://github.com/RyanWangZf/MedCLIP)
- **机器人/视频帧**：RT-1 一类模型使用低分辨率相机帧并按控制周期反复推理，单帧确实是小请求；但同一机器人相邻帧有严格时序与状态依赖，不等价于可自由重排的独立请求。只有“多机器人/多摄像头 fleet gateway”才形成请求级并发，而且动作模型与现有 CLIP 系统差异较大。[RT-1 官方仓库](https://github.com/google-research/robotics_transformer)
- **遥感整幅影像、病理切片、长视频**：即使某些模型最终把每块 resize 到 224，只要一次 API 请求包含大量 tile/frame，其父请求视觉 token 总量仍很大，不属于本课题定义的小请求。RSICD/UCM 只保留“单 tile 独立请求”口径。

## 启动前必须补的两项审计

1. 下载 FashionIQ 后对全部图片实际读取宽高，输出 raw width/height 分布、长宽比、失败 URL 数；在此之前不要写“原生 256×256”。
2. 对每个模型记录 `processor size`、`patch_size`、单图视觉 token 数和是否启用 any-resolution/tiling。只要启用了 LLaVA-NeXT/InternVL/Qwen2-VL 一类动态切片，即使 raw 图低于 1024，也必须按**切片后的总视觉 token**重新判定是否还是小请求。

## 研究边界建议

本方向可正式写为：**针对单图、短文本、低视觉 token 的多模态在线请求，研究共享 GPU 上的并发编码与动态组批，在不改变模型输出的前提下提高吞吐和 SLO 达标率。**

这里“低视觉 token”是核心边界；224–672（最高 1024）只是当前 CLIP ViT-B/32 实验中的可操作尺寸范围，不应被写成跨模型通用定义。

## 第二训练集：NWPU-Captions（2026-09-29）

**明确推荐 NWPU-Captions 作为 RSICD 之后的第二训练集。** 它以 NWPU-RESISC45 为底图，包含 **31,500 张原生 256×256 RGB 遥感图像、45 类、每类 700 张**；NWPU-Captions 论文给出 **157,500 条由 7 名志愿者人工标注的句子**，即每图 5 条 caption。[NWPU-Captions 论文](https://doi.org/10.1109/TGRS.2022.3201474)；[NWPU-RESISC45 论文](https://arxiv.org/abs/1703.00121)；[底图作者数据页](https://gcheng-nwpu.github.io/#Datasets)

对作者标注仓库的 `dataset_nwpu.json` 做结构化统计后，实际划分为 **25,200 train / 3,150 val / 3,150 test（80% / 10% / 10%）**，每类严格为 560 / 70 / 70；每个图像对象都提供 `raw`、`raw_1` 到 `raw_4` 五条描述。[作者标注仓库](https://github.com/HaiyanHuang98/NWPU-Captions) 这比 RSICD 的 10,921 张图更适合做训练和持续请求回放，同时仍保持固定原生小图，不会把 resize、动态切片或尺寸异质性混入“小请求并发”的主变量。

**建议用法**：RSICD 保持主应用和跨数据集对照，NWPU-Captions 用作 CLIP 遥感域微调及固定 256×256 小请求压力源。沿用官方 train/val/test；训练可采用图文对比学习，测试同时报告双向 Recall@K/mR 与系统侧吞吐率、mean/P99、GPU 利用率、SLO 违约率。需要注意，NWPU-Captions 原论文的标准任务是遥感图像 captioning，使用 BLEU-1/2/3/4、METEOR、ROUGE-L、CIDEr；将其用于 CLIP 双向检索属于本项目的任务适配，不能把 Recall@K 写成该论文原始指标。

**候选比较**：UCM-Captions（2,100 图、256×256、每图 5 句）和 Sydney-Captions（613 图、每图 5 句，约 500×500）适合做快速正确性检查，但规模太小，不适合作为第二主训练集。RS5M（约 500 万图文对）和 SkyScript（约 260 万）更适合遥感视觉语言预训练，但来源、尺寸和质量更异质，训练成本也远高于当前单卡条件，会模糊“固定小请求为何适合并发”的机制变量。[RS5M 论文](https://arxiv.org/abs/2306.11300)；[SkyScript 论文](https://arxiv.org/abs/2312.12856)

**许可与下载风险**：NWPU-RESISC45 作者页把底图标为 **CC BY-NC 4.0**，但 NWPU-Captions 标注仓库没有 `LICENSE`，因此不能声称整套图文数据都采用该许可；对外发布标注衍生物前需向 caption 作者确认。仓库中的约 407 MB 图像压缩包使用 Git LFS，曾出现配额导致无法下载的问题，稳妥路径是从 NWPU-RESISC45 作者页下载底图，再配作者仓库的 JSON。此外，[issue #2](https://github.com/HaiyanHuang98/NWPU-Captions/issues/2) 曾报告 `airplane_111.jpg` 缺失，修复 [PR #3](https://github.com/HaiyanHuang98/NWPU-Captions/pull/3) 截至核查时仍未合并；训练前必须检查 31,500 个 JSON 文件名与实际图片一一对应，并记录缺失项。
